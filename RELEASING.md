# Как подготовить и выпустить версию

## Единый источник

`js/product.js` содержит список `releases`, от нового выпуска к старому. Текущий номер вычисляется из первой записи. Интерфейс, уведомление, сведения о продукте, CHANGELOG и имя Git-тега используют этот источник. Схемы JSON-проектов и ключи localStorage имеют собственные версии формата; их не нужно менять при каждом релизе продукта.

`CHANGELOG.md` — производный документ: номера в нём не редактируются вручную. То же относится к копии данных внутри сгенерированного автономного HTML.

## Подготовка следующего выпуска

1. Создайте ветку от актуального `main`. Добавьте запись в начало `releases`: номер SemVer, название, краткое описание `summary`, основные изменения и уровень `importance`: `highlight`, `standard` или `patch`. Уровень выбирается по содержанию, а не выводится из номера. Для ветки PR задайте `status: "unreleased"`, `date: null`, `commit: null`; после создания PR добавьте его реальный номер в `pullRequests`. Не указывайте будущую дату выпуска или несуществующий merge-коммит. Исторические записи сохраните. Для первых выпусков даты взяты из объединения PR в часовом поясе Asia/Yekaterinburg; это указано в истории.
2. При наличии достоверных данных заполните `rights.owner` и `rights.contact` в том же файле. Пустые значения допустимы и не заменяются выдуманными сведениями. Форму «О Shorts Studio» можно использовать для локальной проверки полей; она не редактирует публичную конфигурацию. Лицензию выбирает правообладатель отдельно — автоматически она не добавляется.
3. Обновите производные файлы:

   ```sh
   node scripts/release.cjs changelog
   node scripts/release.cjs check
   python3 scripts/prepare-site.py
   ```

4. Выполните проверки:

   ```sh
   node --test tests/*.test.cjs
   python3 tests/browser.py
   python3 tests/video-browser.py
   python3 tests/media-browser.py
   python3 tests/product-browser.py
   python3 tests/backup-browser.py
   BACKUP_ENTRY=downloads/Shorts-Studio.html python3 tests/backup-browser.py
   python3 tests/pages.py
   ```

   Для браузерных проверок нужны зависимости из `requirements-dev.txt`, Chrome/Chromium и FFmpeg. Дополнительно CI проверяет продукт в WebKit с эмуляцией iPhone и в настоящем Safari через safaridriver на macOS. Успех WebKit не следует выдавать за проверку реального Safari или физического iPhone. Результат Safari и ограничения конкретного браузера записываются в отчёт теста.

   Читайте также предупреждения Safari: ошибка кодека считается прежним ограничением только после воспроизведения на базовом коммите и проверки неизменности исходных модулей. Это подтверждает отсутствие новой регрессии в оформлении продукта, но не успешный экспорт в Safari. Порядок сравнения описан в README.

5. Включите изменения источника, CHANGELOG и обновлённые `downloads` в коммит. Создайте PR в `main`; дождитесь всех обязательных проверок. Автоматическое объединение для выпуска не требуется.

## После ручной проверки, перед выпуском

До ручного выпуска запись остаётся «Ещё не опубликовано» во вкладке и CHANGELOG. Только после одобрения владельца внесите `status: "published"`, фактическую дату и SHA уже проверенного коммита изменений; не придумывайте будущий merge SHA. Перегенерируйте CHANGELOG и автономные файлы, проверьте diff и тесты. Эти изменения и merge/publish не выполняются автоматически. Публикация после объединения зависит от прежнего Pages workflow.

Для небольших исправлений увеличивайте patch; для действительно новых функциональных возможностей — minor. Предполагаемые будущие номера не добавляются в историю как выпущенные.

## Локальная подготовка тега

На чистой, протестированной рабочей копии:

```sh
node scripts/release.cjs info
node scripts/release.cjs tag
```

Для `unreleased` команда откажется создавать релизный тег. Для подтверждённого выпуска команда создаёт **аннотированный локальный** тег на текущем HEAD. Имя берётся из конфигурации. Скрипт не отправляет ветки или теги, не создаёт GitHub Release и не публикует сайт. Существующий локальный тег он не перезаписывает.

Подготовленный в PR тег указывает на коммит ветки PR. После ручного объединения убедитесь, что этот коммит вошёл в `main` и соответствует выпускаемому содержимому:

```sh
git fetch origin main
shorts_release_tag="$(node -p "'v' + require('./js/product.js').version")"
git show --no-patch --format=fuller "$shorts_release_tag"
git merge-base --is-ancestor "$shorts_release_tag" origin/main
git diff --exit-code "$shorts_release_tag" origin/main
```

При обычном merge исходный коммит PR остаётся предком `main`. После squash/rebase это может быть иначе. Если подготовленный тег ещё **не опубликован**, а целевой коммит изменился, проверьте итоговый `main`, удалите только локальный подготовительный тег и создайте его заново на проверенном `main`. Не перезаписывайте опубликованные теги и не используйте force push для выпуска.

## Публикация — отдельное подтверждаемое действие

До прямого подтверждения пользователя не выполняйте отправку тега или создание GitHub Release. Сначала покажите точное имя тега и целевой SHA.

Только после подтверждения отправляется **один конкретный** тег:

```sh
git push origin "refs/tags/$shorts_release_tag"
```

Не используйте `git push --tags`: так можно случайно опубликовать посторонние локальные теги. GitHub Release при необходимости создаётся отдельным разрешённым действием с заметками из CHANGELOG.

Публикация сайта отделена от тега: существующий workflow Pages запускается при изменении `main`, а не при локальном создании или отправке тега. Ветка PR сайт не публикует. Сам PR также не следует объединять без отдельного указания пользователя.
