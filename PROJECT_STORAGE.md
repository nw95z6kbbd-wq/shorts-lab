# Локальное сохранение проектов

Первая версия хранит один текстовый проект и один независимый видеопроект. Это существующие два режима приложения; списка проектов, корзины, ZIP проектов и облака здесь нет. Номер продукта не является номером формата базы.

## Что сохраняется

База IndexedDB `shorts-studio.projects`, версия схемы 1:

| Хранилище | Данные |
| --- | --- |
| `projects` | Записи `editor` и `video`: схема, ревизия, состояние, время и один предыдущий корректный снимок |
| `assets` | Исходные байты изображений, голоса и музыки, MIME, идентификаторы, имена и назначение |
| `meta` | Отметка завершённой миграции и копии исходных строк legacy JSON |

Текстовый проект сохраняет сценарий, правки сцен, выделение и оформление. Видеопроект сохраняет идею, сцены, изображения, движение камеры, переходы, автоматические/ручные длительности, стиль субтитров, формат экспорта, ссылки на исходные голос и музыку, громкости и музыкальные fades.

Исходные медиа не перекодируются для хранения. В IndexedDB записываются ArrayBuffer с исходными байтами и MIME; Blob восстанавливается при чтении. Это обходит обнаруженный в тестовой сборке WebKit отказ подготовки временных Blob/File для IndexedDB. Преобразование в ArrayBuffer выполняется последовательно до транзакции; Base64 не используется. Декодированные AudioBuffer, изображения и временные `blob:` URL создаются заново после открытия страницы. Текстовый сценарий и видеосцены не синхронизируются автоматически. Прежняя кнопка переноса сценария продолжает требовать подтверждения.

Готовые MP4/WebM не сохраняются в базе: скачайте результат или соберите его повторно. Файл `.shorts.json` по-прежнему относится только к текстовому редактору и не содержит видеомедиа. Сгенерированный `downloads/Shorts-Studio.zip` — упаковка приложения, а не архив пользовательского проекта.

## Сохранение и восстановление

1. Текст и настройки сохраняются с задержкой 300 мс, при непрерывном вводе — не позднее запуска очередной записи через 2 секунды. Загрузка нового изображения или аудио дополнительно запускает сохранение сразу после успешного декодирования.
2. Снимок и новые файлы фиксируются одной readwrite-транзакцией `projects` + `assets`. Декодирование и другая асинхронная подготовка выполняются до транзакции; внутри неё используются обработчики IndexedDB без внешних await.
3. `Сохранено на устройстве` появляется после `transaction.oncomplete`. Более поздние правки не получают статус сохранённых от завершившейся старой записи. При нехватке места или прерывании отображается `Ошибка сохранения` и подробное сообщение.
4. Записи одного режима последовательно проходят очередь. Каждая транзакция сравнивает ожидаемую ревизию с текущей. Устаревшая вкладка не может молча заменить новые данные даже при отсутствии BroadcastChannel.
5. При перезагрузке загружается последний завершённый снимок. Если его структура повреждена, используется предыдущий корректный снимок, если он доступен. Автоматическое уничтожение или пересоздание повреждённой базы не выполняется.
6. Старые материалы удаляются только из новой базы и только когда на них не ссылаются текущие и предыдущие снимки обоих режимов. Это не затрагивает исходную legacy-базу.

После восстановления загружаются изображения и обе аудиодорожки. Звук не запускается автоматически: предпросмотр/запись требуют нажатия пользователя. Если материал отсутствует или браузер не может его прочитать, экспорт блокируется. Можно выбрать файл повторно или явно убрать дорожку / переключить сцену на анимированный фон. Ошибка не должна незаметно превращать озвученный ролик в немой.

При ошибке записи текущие правки и новые файлы остаются в памяти вкладки. Не закрывайте её до сохранения нужного текста/видео или устранения ошибки. После освобождения места повторное изменение поля снова запускает сохранение. При конфликте вкладок сначала сохраните нужный результат/скопируйте текст и затем перезагрузите страницу; автоматического объединения правок нет. ZIP-резервная копия полного проекта будет отдельным этапом.

`visibilitychange` и `pagehide` дополнительно пытаются завершить отложенное сохранение, но закрытие страницы не гарантирует выполнение асинхронного кода. Перед закрытием дождитесь `Сохранено`. При аварийном завершении процесса могут потеряться ещё не подтверждённые последние изменения; завершённые транзакции защищают от частично записанной новой ревизии в пределах гарантий браузера.

## Безопасная миграция

При первом запуске новой версии:

- читаются `shorts-studio.project.v1` и `shorts-studio.video.v1` из localStorage;
- два режима проверяются и переносятся в отдельные записи, без объединения сценариев;
- используемые изображения копируются из `shorts-studio.media.v1/images`;
- обе записи, файлы, исходные строки JSON и отметка миграции записываются одной транзакцией;
- при сбое вся новая запись откатывается; следующий запуск может повторить миграцию. Уже прочитанные старые изображения остаются доступны во вкладке для предпросмотра/экспорта, без записи в legacy.

Старые ключи localStorage, их recovery-копии, прежняя база и файлы **не удаляются и не обновляются**. Повреждённый legacy JSON остаётся в старом ключе и копируется в `meta`; приложение показывает предупреждение. Отсутствующий legacy-файл явно учитывается и блокирует экспорт соответствующей сцены. Неудавшееся чтение базы не объявляется успешной миграцией.

Когда перенос завершён, новая база становится источником состояния. Последующее изменение старых ключей обнаруживается и сопровождается предупреждением; новая работа ими не заменяется. При откате опубликованного приложения старая версия увидит оставленные legacy-данные, которые могут быть старее новых правок. Миграция не обеспечивает синхронизацию между старой и новой версиями приложения.

Голос и музыка старой версии существовали только в памяти: восстановить их после уже случившегося закрытия вкладки невозможно. В первый раз выберите исходные аудиофайлы заново; последующие загрузки сохраняются в новой базе.

## Safari и ограничения хранения

- IndexedDB, наличие места и возможность записи проверяются фактическими операциями. Наличие API само по себе не гарантирует успешную запись бинарных данных.
- При недоступной IndexedDB приложение продолжает работать в памяти, а автосохранение явно недоступно. Старые данные не переписываются fallback-записями в localStorage. После устранения причины откройте страницу повторно для новой проверки.
- При невозможности проверить старые localStorage-данные миграция откладывается, чтобы не объявлять пустую базу успешно перенесённой.
- Обрабатываются ошибки квоты, прерывания, тайм-ауты открытия/транзакций и блокировка обновления схемы другой вкладкой. Соединение закрывается при `versionchange`; база не удаляется для «исправления» ошибки.
- В приватном режиме данные могут исчезнуть после закрытия приватного сеанса. Очистка данных сайта, вытеснение браузером и нехватка диска также могут удалить локальное хранение. Постоянного хранения навсегда эта версия не обещает; запрос `navigator.storage.persist()` здесь ещё не добавлен.
- Для `file://` поведение зависит от браузера. Для регулярной работы используйте постоянный адрес GitHub Pages или localhost. Сайт остаётся статическим: сервер генерации не нужен.
- Хранилище привязано к origin. Смена домена, браузера, профиля или порта localhost не переносит проекты. Разные пути одного origin не изолируют базы друг от друга.
- Большие изображения и декодированное аудио требуют оперативной памяти. Существующие ограничения файлов сохранены; на смартфоне процесс может быть выгружен системой. Кодеки экспорта и декодирования всё ещё зависят от браузера.

## Проверка

Нужны зависимости из `requirements-dev.txt`, Chromium и FFmpeg/ffprobe:

```sh
python tests/project-db-browser.py
python tests/project-migration-browser.py
python tests/project-browser.py
python scripts/prepare-site.py
PERSISTENCE_ENTRY=downloads/Shorts-Studio.html python tests/project-browser.py
```

Первый тест запускает только репозиторий, без подключения редакторов: проверяет атомарность, предыдущую ревизию, отсутствие новых битых ссылок, rollback при квоте, CAS двух писателей и повтор после прерванной миграции. Второй проверяет настоящий адаптер миграции: сбой записи отметки миграции откатывает все новые данные; legacy остаётся неизменной; повтор успешно переносит два независимых состояния; поздняя запись старой вкладки не перезаписывает новую работу.

Третий тест создаёт старые данные, переносит изображение, загружает второе изображение и две WAV-дорожки через интерфейс, меняет настройки и полностью завершает процесс браузера. Затем он запускает новый процесс с тем же профилем, сравнивает состояние и байты исходных файлов, скачивает SRT и записывает настоящее видео. FFmpeg проверяет размер 720×1280, длительность, изображения по порядку, обе звуковые частоты и отсутствие чёрных кадров. Дополнительно проверяются конфликт вкладок, отказ записи с сохранением прежнего состояния и блокировка экспорта при потере аудио.

Для WebKit:

```sh
python -m playwright install --with-deps webkit
PERSISTENCE_BROWSER=webkit python tests/project-db-browser.py
PERSISTENCE_BROWSER=webkit python tests/project-migration-browser.py
PERSISTENCE_BROWSER=webkit python tests/project-browser.py
```

Если сборка WebKit не предоставляет кодек записи, тест сообщает ограничение и проверяет сохранение и восстановление; это не считается подтверждением экспорта в данном движке. Настоящий Safari на macOS проверяется отдельным заданием Actions: сохранение оригинальных PNG/WAV, сравнение SHA-256 после перезагрузки, восстановление настроек и реальная запись через интерфейс. Перезапуск процесса с сохранением профиля проверяется в Chromium/WebKit. Физический iPhone и принудительная выгрузка Safari системой требуют отдельной ручной проверки.

Ручной сценарий: загрузите изображения, голос и музыку, измените настройки, дождитесь `Сохранено`, полностью закройте браузер и откройте тот же адрес в том же профиле. Проверьте имена файлов, предпросмотр, SRT и скачанное видео. Не очищайте данные сайта между запусками.
